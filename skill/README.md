# 技能包 —— 从手势识别项目沉淀的可复用能力

> **一句话**：一支陌生队伍拿到本目录，能否直接用在**自己的**题目上？
> 本目录每一项都按这个标准组织。

适用工具链：**Vivado / Vitis 2025.2**（赛题允许 2026.1，未验证）
适用器件：AMD 7 系列 / Zynq-7000（本项目在 `xc7z020clg400-1` 上验证）

## 目录

| 项 | 类型 | 通用性 | 说明 |
|---|---|---|---|
| [`pynq/`](#1-pynq--四个pynq工具) | 校验脚本 | **通用（加分项）** | 4 个独立 Python 工具，与题目无关 |
| [`pitfalls/`](#2-pitfalls--踩坑清单) | 踩坑清单 | 通用 | 19 条 Vivado 踩坑，含触发条件与排查步骤 |
| [`self-correction/`](#3-self-correction--纠错轨迹) | 提示词工作流 | 通用 | 从"误判"到"实测推翻"的方法论 |

> ⚠ **本目录不含**与手势识别题目绑定的内容（那些在 `../docs/`）。
> 这里只放**换题目、换板卡仍然可用**的东西。

## 1. `pynq/` —— 四个 PYNQ 工具

**类型**：校验脚本（赛题 §3.3.5.2 的"校验脚本"类）
**通用性**：**高** —— 四个工具都只依赖 `.hwh` / 比特流产物，不依赖本项目任何代码。

| 工具 | 解决什么问题 |
|---|---|
| `ip_contract.py` | **原始 `.hwh` 不要直接读** —— 实测 307 KB ≈ 77,000 tokens。本工具压成 < 3 KB 的紧凑 JSON 契约（寄存器偏移、位域、地址范围） |
| `gen_host_stub.py` | 从契约**一次生成三份**主机侧代码（PYNQ Python 驱动 / 裸机 C 头文件 / 测试骨架），消掉"同一个偏移抄三遍"的错误源 |
| `golden_compare.py` | 硬件输出 vs 参考输出**逐位比对**，报出**第一个**不一致的下标与期望/实际值；另可从 `csynth.rpt` 抽指标生成对比表 |
| `dma_guard.py` | DMA 搬运 + cache 一致性封装。缓存漏维护**不报错、只出错数据**，这是最需要封装的一处 |

### 使用方法

```bash
# 1) 从 .hwh 提取契约（不要直接 Read .hwh）
python ip_contract.py board.hwh
python ip_contract.py board.hwh --ip my_accel_0 --json contract.json

# 2) 从契约生成主机侧代码
python gen_host_stub.py contract.json --ip my_accel_0 --lang py -o driver.py
python gen_host_stub.py contract.json --ip my_accel_0 --lang c  -o driver.h

# 3) 输出比对（失败时定位到首个不一致点）
python golden_compare.py compare hw_out.bin golden.bin --shape 96x96

# 4) 采集 HLS 指标，生成"优化前后对比"表
python golden_compare.py report --csynth csynth.rpt --impl impl.rpt
```

### 失效条件

- `ip_contract.py` 依赖 `.hwh` 的 XML 结构。**Xilinx 大版本变更可能改结构**
  （本项目在 2025.2 验证）。解析失败时先看工具报的是哪个标签找不到。
- `gen_host_stub.py` 生成的代码是**骨架**，不保证业务逻辑正确 ——
  它保证的是"寄存器偏移与位域没抄错"。
- `dma_guard.py` 的 cache 操作针对 Zynq-7000 的 ARM Cortex-A9。
  **Zynq UltraScale+ / Versal 的缓存架构不同**，不可直接套用。
- 四者都**不依赖本项目**，但都**依赖 PYNQ 或裸机环境** —— 无板时只能做静态检查。

> **已验证的效果**：`ip_contract.py` 的压缩比（307 KB → < 3 KB）是实测的；
> 其余三个工具的逻辑经主机侧自检，**未上板验证**。

## 2. `pitfalls/` —— 踩坑清单

**类型**：踩坑清单（赛题 §3.3.5.2 的"踩坑清单"类）
**通用性**：**高** —— 都是 Vivado / Vitis 的行为，与题目无关。

**为什么值得单独成篇**：这些坑的共同特征是 **工具不报错，或报错位置离真正原因很远**。
赛题答辩要点里明确提到"能讲清工具静默失败怎么发现、怎么定位、怎么验证的队伍，
可信度显著更高"。

**每一条都按三段式写**：
1. **现象** —— 你看到什么（通常是一句莫名其妙的报错）
2. **根因** —— 实际发生了什么
3. **对策 + 验证** —— 怎么改，以及**用什么命令证明改对了**

⚠ **重点看第 16–19 条** —— 那 4 条来自本项目最后一次集成，全都是
**"工具全流程通过、只有上板才暴露"** 的类型，前 15 条里没有。

### 失效条件

- 坑是**工具版本的函数**。本项目全部在 2025.2 上复现，
  **换到 2024.2 / 2026.1 可能不再触发，也可能新增别的**。
- 第 17 条（`launch_runs` 对失败 run 不做事）依赖 Vivado 的 Runs 机制，
  用 GUI 手动跑流程不会遇到。
- 清单**不追求穷尽** —— 它是本项目的真实记录，不是工具行为手册。

## 3. `self-correction/` —— 纠错轨迹

**类型**：提示词工作流（赛题 §3.3.5.2 的"提示词工作流"类）
**通用性**：**中** —— 方法论通用，具体案例与本项目绑定。

**核心内容**：本项目的开发过程中，**多处结论先被写进文档、后被实测推翻**。
把这些"误判 → 实测 → 更正"的轨迹记录下来，比只写正确结论更有用，
因为它展示的是**怎么发现自己在错**。

三个反复出现的误判模式：

| 模式 | 案例 | 教训 |
|---|---|---|
| **把"另一个文件里没有"当成"这里也没有"** | 误判 `io_xclk` 缺引脚约束（实际 `.xdc` 里一直有） | 判断约束在不在，要 `grep` 约束文件或回读实现报告 |
| **只看直接产物，不看谁在消费它的后果** | 误判 `Could not open 'C'` 是"无害噪声"（实际会让批处理脚本中断） | "是不是无害"取决于**谁在消费它的后果** |
| **验证了"函数被调用"就以为验证了"行为正确"** | 重试逻辑用桩函数验证过，但真实的 `launch_runs` 用法错了 | 桩函数验证的是**控制流**，不是**被调用者的真实语义** |

### 使用方法

把这三个模式当成**写结论前的自检清单**：
1. 我这个结论是从**哪个文件**读出来的？有没有可能它在别处？
2. 这个错误**谁在消费**它的后果？（人 / 脚本 / 下游工具）
3. 我验证的是**控制流**还是**真实语义**？桩函数/单元测试会不会掩盖语义错误？

### 失效条件

- 这是**方法论，不是工具** —— 没有可执行命令，靠人自检。
- 三个模式来自**单一项目**的观察，不构成统计结论。
- **不适用于**：需求本身的误解（那要靠对齐需求，不是靠自检）。

## 附：本技能包与 `docs/` 的边界

| 放哪 | 判据 |
|---|---|
| `skill/`（本目录） | **换题目、换板卡仍然可用** |
| `../docs/` | 与手势识别这个**具体题目**绑定（接口契约、引脚映射、上板步骤） |

拿不准时问一句：**"这个内容对做别的题目的队伍有用吗？"**
有用 → `skill/`；只是本项目的记录 → `docs/`。
