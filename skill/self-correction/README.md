# 纠错轨迹 —— 怎么发现自己在错

> 本项目的开发过程中，**多处结论先被写进文档、后被实测推翻**。
> 记录这些轨迹比只写正确结论更有用，因为它展示的是**怎么发现自己在错**。
>
> 每条都按四段式：**结论 → 实测 → 为什么错 → 现在怎么防**。
> 案例来自本项目，但**四个模式是通用的**。

---

## 模式 1 · 把"另一个文件里没有"当成"这里也没有"

### 案例：`io_xclk` 缺引脚约束

**结论**（写进了文档，还列为阻塞项）
> "`io_xclk` **没有任何引脚约束**，线是悬空的。"

**实测**

```bash
$ grep io_xclk video_io.xdc
183:set_property -dict { PACKAGE_PIN Y18 IOSTANDARD LVCMOS33 } [get_ports io_xclk]

$ grep io_xclk <impl>/bd_video_wrapper_io_placed.rpt
| Y18 | io_xclk | ... | OUTPUT | LVCMOS33 | ... | FIXED | ...
```

**约束一直在**，`Constraint = FIXED`，而且实现报告能证明。

**为什么错**

我当时读了一份**规格表**，里面没列 `io_xclk`，于是断定"约束文件里没有它"。
**两个文件是两回事**，我却把"在 A 里没找到"直接当成了"在 B 里不存在"。

**现在怎么防**

> 判断"某个约束在不在"，**`grep` 约束文件，或回读实现产物报告**。
> 不要从**别的文档**推断。

**通用形式**：任何"X 不存在"的结论，都必须来自**X 所在的文件**，
不能来自它的转述、摘要、或另一份规格表。

## 模式 2 · 只看直接产物，不看谁在消费它的后果

### 案例：`Could not open 'C'` 被判定为"无害噪声"

**结论**（写进了文档）
> `[Common 17-1257/354]` …… **忽略**。返回码 0，不影响任何产物。

**实测**

它对**产物**确实无害（那个 run 的 `.dcp` 照样生成了），
但**对流程致命**：

```
ERROR: [Vivado 12-13638] Failed runs(s) : '<run 名>'
ERROR: [Common 17-39] 'wait_on_runs' failed due to earlier errors.   ← 脚本在此中断
```

Vivado 把这个瞬时失败**判定成 run 失败**，`wait_on_run` **直接抛错返回**。
后果是：**后面的 XSA 导出根本没执行到**。

**为什么错**

我的判断依据是"产物齐全 + 返回码 0"。
**没考虑它对上层批处理流程的影响** —— 而那个流程才是真正在消费这个错误的。

**现在怎么防**

> 判断一个错误是否无害，问一句：**谁在消费它的后果？**
>
> - 只有人看日志？→ 影响小
> - **有脚本/下游工具依赖"没报错"这个信号？→ 可能致命**

**通用形式**：错误的危害不在于它**做了什么**，而在于**谁把它当成信号**。

## 模式 3 · 验证了"控制流"就以为验证了"行为"

### 案例：重试逻辑是"假重试"

**结论**
> 加了重试逻辑，并用桩函数验证过 —— `reset_run` 1 次、`launch` 2 次，符合预期。

**实测**

真实环境里，重试**同一秒就返回，根本没跑**：

```
>>> synth_1 进度 0% —— 第 1 次未完成
>>> 重试...
[21:38:34] Waiting for synth_1 to finish...
[21:38:34] synth_1 finished        ← 同一秒返回
```

**根因**：`launch_runs` 对**已失败的 run 不做任何事**（它认为"跑过了"）。
必须先 `reset_run` 清掉失败状态。

**为什么错**

桩函数验证的是"**我的代码有没有按预期调用** `launch_runs`" ——
那是**控制流**。但 `launch_runs` 的**真实语义**（对失败 run 无操作）
桩函数**模拟不出来**，因为它是我自己写的，我按自己的理解实现它。

**现在怎么防**

> 桩函数/单元测试能证明**控制流**，**证明不了被调用者的真实语义**。
> 涉及外部工具（Vivado / 编译器 / 硬件）时，**最终必须在真实环境跑一次**，
> 而且要看**真实日志**，不是看"没报错"。

**通用形式**：**用自己写的 mock 验证与外部系统的交互，是循环论证**。
mock 按你的理解实现，它当然会通过。

## 模式 4 · 按"我挑的范围"检查，而不是"完备的范围"

### 案例：同步文档时漏了 7 个 README

**结论**
> "已同步 7 个文件 + 新增上板测试指南" —— 看起来完整。

**实测**

用户问了一句 "sw 里面的 readme 没有更新吧"，我改完 `sw/README.md` 后
换成**遍历仓库所有 `.md`** 重查，才发现**一共漏了 7 个**：

| 我上一轮 | 实际 |
|---|---|
| 对比了 10 个我挑的文件 | 仓库有 11 个 `.md` |
| `sw/README.md` 没查 | 有过时陈述 |
| `src_hls/README.md` 没查 | 有"占位表/唯一阻塞项"过时 |
| `vivado/README.md` 没查 | WNS 过时 + **第 15 条结论被本轮推翻** |
| `host/README.md` 判"相同"就跳过 | **"相同" ≠ "内容正确"**，也有过时 |

**为什么错**

我按"**我记得改过的文件**"列清单，而不是"**仓库里所有的文件**"。
前者依赖我的记忆，后者才是完备的。

**现在怎么防**

> 核对一致性时，**先枚举全集，再逐个判定**：
> ```bash
> git -c core.quotepath=false ls-files -z '*.md' | while read -d '' f; do ... done
> ```
> **不要**从"我改过哪些"倒推"哪些需要改"。
>
> 另外：**"两个文件内容相同"不等于"内容正确"** ——
> 两边可能**同时过时**。

**通用形式**：**检查范围的完备性，比检查本身更重要**。
用"我做了什么"定义范围，等于用记忆定义范围。

## 附：一次典型的自我纠错链

本项目最后阶段的真实序列（**每一步都依赖上一步的输出**）：

```
① 用户报告"实现无法完成" + 一段 DRC 报错
      ↓  读日志
② 发现 synth_design -top 是子模块名（不是顶层）
      ↓  追为什么
③ 发现 BD 重建 wrapper 时把它从工程文件表挤掉
      ↓  加断言防复发
④ 断言生效后，暴露下一个问题：open_run 顺序错
      ↓  修正
⑤ 修正后重跑，暴露第三个：重试没绑 reset_run
      ↓  修正
⑥ 再跑，暴露第四个：并发竞态打断了流程
      ↓  加重试
⑦ 跑通
```

**关键观察**：**每个修复都暴露下一个问题**，而不是同一个问题反复。
这说明修的是真问题。

> 如果修完还是同一个症状 —— 那是**没找到根因**，不是"还有别的问题"。
