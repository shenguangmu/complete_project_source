# HLS 优化对照：一次被证伪的假设，和一次找对地方的排查

> 2026-09-18 · Vitis HLS **2025.2** · `xc7z020clg400-1` · 时钟 **10 ns（100 MHz）**
>
> 本文件是赛题 §3.3.5.5「性能与资源优化效果」（20 分）要的
> **优化前后对比表**，以及一次**有数据的负结果**。

---

## 一、动因

`vivado/build-report.md` 记录实现后 **DSP = 61（27.73%）**，
其中 HLS 的 `gesture_preproc` 占 **71 个（csynth 口径）**。
DSP 是全设计最紧的资源之一，先查它去了哪。

旧注释给过一个结论：

> "DSP 来自若干带 **16 位常数魔数**（如 21846）的乘法器，
> 不是 `oy*96` 这类常量乘 —— HLS 对常量乘本来就用移位。"

**这个结论是错的。** 下面是查证过程。

---

## 二、查清 DSP 的真实去向

`csynth.rpt` 的 **Bind Op Report** 段把每个算子标了 DSP 占用。
`morph_stage` 占 56 个，其中 **55 个在腐蚀流水线**
（`morph_stage_Pipeline_VITIS_LOOP_578_4...`）里：

| 乘法器 | 位宽 | **DSP 个数** | 来源变量 |
|---|---|---:|---|
| `mul_64ns_66ns_129_5_1_U134` | **64×66→129** | **16** | `mul_ln590` |
| `mul_64ns_66ns_129_5_1_U135` | **64×66→129** | **16** | `mul_ln590_1` |
| `mul_64ns_66ns_129_5_1_U136` | **64×66→129** | **16** | `mul_ln590_3` |
| 其余 8 个 | 14×16→29 等 | 各 1 | 小算子 |
| **合计** | | **55** | |

**全文没有 21846 这个常数。**
真正的大头是 **3 个 64×66→129 位乘法器，每个吃 16 个 DSP，合计 48 个**，
占全设计 71 个 DSP 的 **68%**。

> 它们的来源是腐蚀循环里的下标：
> ```cpp
> for (int dy = -1; dy <= 1; dy++)      // #pragma HLS UNROLL
>   for (int dx = -1; dx <= 1; dx++) {  // #pragma HLS UNROLL
>       const int yy = oy + dy, xx = ox + dx;
>       if (...) p = r1[yy * width + xx];   // ← 这里
>   }
> ```

---

## 三、对照实验：换四种写法，看 DSP 会不会降

**每次都是干净重跑**（`open_project -reset`），**TB 逐位比对通过**
（不是只跑综合就下结论）。

| 改法 | **DSP** | **LUT** | FF | BRAM | morph LUT | 语义 |
|---|---:|---:|---:|---:|---:|---|
| **基线**（`width` 变量作步长） | **71** | **13,144** | **11,177** | 34 | 5,214 | ✅ |
| ① 步长 `width` → 编译期常量 `G::OW`(=96) | 71 | 13,144 | 11,177 | 34 | 5,214 | ✅ |
| ② 9 个读全部显式展开 | **86** ↑ | 13,377 ↑ | 11,698 ↑ | 34 | 5,447 ↑ | ✅ |
| ③ 探针：索引换成固定值 `r1[0]` | **15** ↓↓ | 10,235 | 8,123 | 33 | — | ❌ 故意破坏 |
| ④ 步长换模板参数（历史结论） | 71 | — | — | — | — | ✅ |

**读法：**

- **① 毫无变化** —— 即使步长在编译期已知是 96，HLS 照样综合出宽乘法器。
  说明根因**不是"步长未知"**。
- **② 反而更差（+15 DSP，+233 LUT）** —— 手写展开让 HLS 把 **4 个**
  乘法器都摆上流水线，代价比原来还高。
- **③ 是决定性探针** —— 把索引换成与 `oy/ox` 无关的固定值，
  DSP 从 71 掉到 **15**，3 个 64 位乘法器**全部消失**。
  **这证明根因确实是这段索引算术**（不是魔数、不是 `oy*96` 之类的常量乘）。
- 但 **① 和 ② 合起来说明：找到了根因，却改不掉。**
  HLS 对归纳变量 `oy`/`ox` 的范围推断不足，我们无法在不改语义的前提下
  让它把下标识别为窄位宽地址。

> ⚠ **结论：这条优化路径到此为止。** 记录在此，
> 免得后人（或下一个大模型）再花一轮去试同样的三种写法。

## 四、关于时序：`+0.265 ns` 不是本设计的余量

旧注释还有一句：

> "展开写会让关键路径变长，吃掉仅剩的 `+0.265 ns` 时序余量。"

**这句话本身也站不住 —— 因为 `+0.265 ns` 根本不是我们的数。**

查布线后的 `bd_video_wrapper_timing_summary_routed.rpt`：

**全设计 10 条最差 setup 路径，全部属于 `bd_video_v_tc_0`**：

```
Slack (MET) :   0.265ns
  Source:  .../bd_video_v_tc_0/<hidden>/<hidden>/<hidden>   ← AMD 的 v_tc IP
  Target:  .../bd_video_v_tc_0/<hidden>/<hidden>/<hidden>
  Path Group:         clk_fpga_0
  Logic Levels:       1  (LUT3=1)
  Data Path Delay:    9.764ns  (logic 0.642ns (6.6%)  route 9.122ns (93.4%))
  net (fo=433, routed)   9.122ns      ← 扇出 433 的高扇出网
  Timing Exception:   MaxDelay Path 10.000ns -datapath_only
```

| 事实 | 含义 |
|---|---|
| 逻辑只有 **0.642 ns**，布线 **9.122 ns** | **不是逻辑深度问题**，是一条扇出 433 的网绕远了 |
| 路径两端都在 `<hidden>` 的加密 IP **内部** | **改我们的 RTL/HLS 对它零影响** |
| 带 IP 自带的 `-datapath_only` 例外 | 该例外**不含时钟不确定度**，所以它的 slack 天然偏小 |

**对比 HLS 侧的估计：**

| | 目标 | 估计值 | 余量 |
|---|---|---|---|
| `morph_stage` 腐蚀流水线（csynth） | 100 MHz | **143.31 MHz** | **+43%** |
| `clk_fpga_0` 整体（布线后） | 100 MHz | — | +2.65%（v_tc） |

HLS 说 143 MHz、布线后整体只有 100 MHz —— **差着 30%**。
差异不在于 HLS 估错，而在于**整体最差路径是 IP 的布线，不是我们的流水线**。

## 五、时序这条线，能做什么 / 不能做什么

### ❌ 不能做（已排除）

| 想法 | 为什么不行 |
|---|---|
| 优化 HLS 流水线 | 它不是关键路径（HLS 估 143 MHz，余量 43%） |
| 优化我们自己的 RTL | 10 条最差路径没有一条属于 `dvp_capture` / `gesture_preproc` |
| 手写展开降 DSP | 实测反而更差（见 §三②） |

### ⚠ 可以试（有明确代价）

| 做法 | 预期 | 代价 / 风险 |
|---|---|---|
| **`v_tc` 的 Reset / `Clk` 上 `set_property CLOCK_DEDICATED_ROUTE FALSE`** | 否 | 动布线约束，可能引入新问题，**风险大于收益** |
| **把 `clk_fpga_0` 降到 80 MHz** | v_tc 的 9.1 ns 布线压力缓解 | **违反赛题性能目标**，28 FPS 掉到 22 FPS |
| **去掉 `-datapath_only` 例外** | 数字会"变好看"（加上时钟不确定度） | **粉饰**，数字不再反映真实可达频率，不做 |
| **给 v_tc 的扇出网加 `MAX_FANOUT`** | 可能缩短布线 | 加密 IP 内部网，**约束不进去** |

### ✅ 该做的

**什么都不改，并在报告里如实标注。**

理由：这 10 条路径都在 AMD 官方 IP 内部，且属于
"高扇出 + 布线主导"的物理实现问题。对本作品而言：

- 它是 **IP 可用性问题，不是性能瓶颈** —— 设计已 `All user specified
  timing constraints are met.`，对 v_tc 的功能没有影响
- **换布线的随机波动比它大**：同一设计三次实现为
  **+0.873 / +1.177 / +0.265 ns**（见 `../vivado/build-report.md` §3.1）
- **任何"优化"都是在 IP 外面猜 IP 里面的布线**

## 六、这次实验的方法论产出

1. **DSP 归属必须逐条查 Bind Op Report。**
   本项目在这个问题上**连续推断错三次**（先归给 `thresh_stage`
   的除法，再归给"16 位常数魔数"，再归给"编译期步长"），
   最后由**一个固定值探针**一锤定音。
   工具：`skill/pynq/golden_compare.py report <模块>_csynth.rpt`

2. **"找到了根因"≠"能改"。**
   §三的③证明了根因，①和②证明了改法全都不划算。
   **两条要一起写进结论**，否则下一个人会以为根因没找到而重来一遍。

3. **引用时序数字前，先确认它属于谁。**
   `WNS=+0.265` 被引用了四个文档，没人查过它属于哪个模块。
   一查才发现是 AMD IP 的，与我们的优化工作无关。
