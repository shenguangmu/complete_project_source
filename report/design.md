## 一、选题背景与创新点

### 1.1 选题：嵌入式手势识别

摄像头实时采集 → PL 侧预处理 → 得到手部轮廓 → 神经网络分类。

**解决的问题**：手势交互需要**低延迟**（跟随动作，不是按一下等一秒）。
这正好落在 FPGA 的强项上 —— **确定性的低延迟流水线**，
而不是 CPU 的"算得快但抖动大"。

### 1.2 面向的竞赛方向

赛题 §3.3.2 的推荐方向里，**"视觉识别"与"图像预处理加速"**都在列。
本作品的定位是**完整的 FPGA 作品**：从摄像头采集一路做到分类结果。

### 1.3 创新点

#### ① 异构划分沿"数据量 × 操作次数"这条线切，而不是沿"难易"切

这是本作品**最核心的设计判断**（详见 §三）。

常见做法是把 CNN 也塞进 PL —— 本作品**明确否掉**，理由是可量化的：

| 约束 | XC7Z020 实际值 | 微型 CNN 全并行的需求 | 判断 |
|---|---|---|---|
| DSP48E1 | **220** | `Conv(1→8, 3×3)` 单层 = 72 个乘法器 | **单层就吃掉 1/3** |
| LUT | 53,200 | 多层流水 + 权重 ROM 寻址 | 会超 50% |
| 动态功耗 | 现有设计约 1.7 W | 全并行会顶到板卡供电/散热上限 | 有风险 |
| 开发工期 | — | 自研 line buffer + 权重调度 + 定标 | **以月计** |
| **替代方案** | — | **Cortex-A9 (650 MHz) 跑定点推理** | **10–30 ms/帧** |

**关键判断**：目标 30 FPS，PS 侧 30 ms/帧**完全够用** ——
因为**瓶颈根本不在推理，在摄像头采集与预处理**。

> **答辩时会被问，所以提前写清**：不是"PL 做不到"，
> 而是**"用最贵的资源解最容易的问题"**。

#### ② 用"接口契约"解耦分工，而不是用接口定义解耦

`DDR 里 96×96 uint8 灰度 buffer` 是**唯一**的跨侧边界（详见 §三）。
两侧各自把它当黑盒 —— **这让 CNN 侧可以在 PC 上独立开发调试**，
不受板子是否到货影响。

#### ③ 把"验证"当成设计的一部分，而不是收尾动作

本作品对每一层都设了**独立的验证手段**（见 [§四](#四优化过程) 与 `../skill/self-correction/`），
且明确区分"已验证 / 未验证"。这个习惯直接产出了
[`../skill/`](../skill/README.md) 里那套可复用的东西。

### 1.4 前人做过什么

| 参考 | 复用了什么 | 区别 |

| **Sobel 加速器**（本仓库 `legacy/sobel/`，已跑通） | **行缓存骨架**（3 行 BRAM + 3 级列移位寄存器） | 本作品把它重排到 96×96 上跑完整链 |

## 二、设计原理与功能框图

### 2.1 系统总览

```
                    ┌──────────────── PYNQ-Z2 (XC7Z020) ────────────────┐
                    │                                                   │
  OV5640            │   PL (可编程逻辑)              PS (Cortex-A9)      │
  ┌────────┐        │  ┌──────────────────┐        ┌─────────────────┐ │
  │ 500万   │  DVP   │  │ 采集 → 灰度 →    │        │ PYNQ Linux      │ │
  │ 摄像头  ├───────►│  │ 高斯 → Sobel →   │  DDR   │  + Jupyter      │ │
  │        │ 14根线 │  │ 自适应阈值 →     ├───────►│                 │ │
  └────────┘        │  │ 形态学 → ROI     │  512MB │  ┌───────────┐  │ │
                    │  └──────────────────┘        │  │ 轻量 CNN  │  │ │
                    │         ▲                    │  │ (他人负责) │  │ │
  ┌────────┐        │         │ VDMA               │  └───────────┘  │ │
  │ 显示器  │◄───────┤  HDMI Out ◄─────────────────┤                 │ │
  └────────┘        │                              │  结果叠加显示    │ │
                    └──────────────────────────────┴─────────────────┘ │
                    └───────────────────────────────────────────────────┘
```

### 2.2 数据通路（两条，从 DDR 分叉）

```
【显示通路】摄像头原图直通，与预处理完全解耦
 dvp_capture ─AXIS(16bit)─► VDMA S2MM ─► HP1 ─► DDR(帧缓存,3帧)
                                                    │
                        VDMA MM2S ◄── HP2 ◄─────────┘
                             │
                             ▼
                     v_axi4s_vid_out ─► （并行视频；TMDS 编码器未做）

【CNN 通路】从 DDR 取同一帧
 DDR(帧缓存) ─► dma_in(MM2S) ─► gesture_preproc ─► dma_out(S2MM) ─► DDR(96×96)
                                                                        │
                                                              PS 侧 CNN 读这里
```

**为什么从 DDR 分叉，而不是从采集侧（`axis_broadcaster`）分叉**：

broadcaster 要求**所有输出都 ready 才接收输入**。
而 `gesture_preproc` 是 HLS 的 `ap_ctrl_hs` 模式 ——
**未 `ap_start` 时 `tready=0`**。CNN 不需要 30 fps，预处理大部分时间空闲，
于是 `gesture_preproc` 空闲 → broadcaster 反压 → VDMA 收不到数 →
**HDMI 显示也一起卡死**。这个反压是**常态化的，不是偶发**。

DDR 分叉的代价是多一次 DDR 往返（614 KB/帧读），三个 HP 口各自独立，占比很小。

### 2.3 时钟域

| 时钟 | 频率 | 来源 |
|---|---|---|
| `clk_fpga_0` | **100 MHz** | PS7 `FCLK_CLK0` |
| `fpga_pl_clk0` | 100 MHz | 同上 |
| `cam_pclk` | **24 MHz** | 摄像头 PCLK（外部输入） |
| `clk_wiz_xclk/clk_out1` | **24 MHz** | Clocking Wizard 输出 → `io_xclk` |

**跨时钟域**：摄像头 PCLK 域 → 系统 100 MHz 域，由 `async_fifo`
（**格雷码指针 + 双时钟**，标准 CDC 做法）处理。

> Clocking Wizard：100 → 24 MHz，**M=12 / D=1 / O=50，VCO = 1200 MHz**。
> **非整数分频，必须用 MMCM**（简单分频做不到）。

## 三、软硬件划分依据与接口设计

### 3.1 划分依据

**一条线**：**PL 做"每像素一次操作"的带宽型任务；PS 做"需要循环迭代与权重"的算力型任务。**

| 判据 | 用 Verilog | 用 HLS | 放 PS |
|---|---|---|---|
| 需要精确控制时钟域/边沿 | ✅ DVP 采集、SCCB 时序 | ❌ | ❌ |
| 需要例化原语（MMCM/IOBUF） | ✅ XCLK 生成、SDA 三态 | ❌ | ❌ |
| "每像素一次运算"的规整流水 | ❌ | ✅ 灰度/滤波/阈值/形态学 | ❌ |
| 需要频繁改参数调优 | ❌ | ✅ 阈值/增益/核大小 | ❌ |
| **需要循环迭代 + 权重的推理** | ❌ | ❌（占满 DSP） | ✅ **CNN** |

**具体分工**：

| 侧 | 承担 |
|---|---|
| **PL 全部**（本项目） | DVP 采集、SCCB 配置、图像预处理链、VDMA、HDMI 输出、DDR 中继 buffer |
| **PS**（他人） | 模型训练、量化、推理、后处理 |
| ~~PL 侧 CNN 加速~~ | **已评估否决**，理由见 §一.3.① |

### 3.2 接口契约（**唯一的一条边界**）

| 项 | 值 |
|---|---|
| **位置** | PS DDR，由 PL 侧的 `dma_out` 写入 |
| **格式** | `uint8` 灰度，行优先连续存放 |
| **尺寸** | **96 × 96**（9,216 字节） |
| **对齐** | 4 字节对齐（DMA 要求） |
| **取值范围** | 0–255，**不做归一化**（归一化由 CNN 侧负责） |
| **物理地址** | 由 PL 侧驱动分配后**写入寄存器**告知 CNN 侧，**不硬编码** |

**为什么这样定**（每条都有理由，不是随手定的）：

- **不归一化** → 归一化是模型侧的事，PL 不该替它做决定
- **地址不硬编码** → 让 CNN 侧可以在 PC 上独立开发调试，不受板子是否到货影响
- **裸 `.bin` 无头** → 加文件头就要两侧同步解析逻辑；裸二进制任何工具都能 `fread`

**握手寄存器**（轮询，暂不用中断）：

| 偏移 | 名称 | 方向 | 含义 |
|---|---|---|---|
| `0x00` | `CTRL` | 写 | bit0 = `capture_start` |
| `0x04` | `STATUS` | 读 | bit0 = `frame_ready`，bit1 = `busy` |
| `0x10` | `INPUT_ADDR` | 读/写 | 96×96 buffer 的物理地址 |
| `0x18` | `FRAME_SEQ` | 读 | 帧序号（丢帧检测用） |

> ⚠ **实现上注意**：HLS 生成的控制寄存器里，
> **`AP_DONE` / `AP_IDLE` 在 `CTRL`(0x00) 的 bit1–bit3**，
> **不在 `0x04`**（`0x04` 是 `GIER`）。
> 这是个经典误用，且**主机仿真发现不了**（仿真自己造了个假 STATUS 值）。

### 3.3 为什么预处理链是"重排后在 96×96 上跑"

预处理链的**标称输入是 640×480**，但**实际计算全部在 96×96 上进行**：

```
crop_scale（640×480 → 96×96）→ 高斯 → Sobel → 自适应阈值 → 闭运算
                              └──────── 全部在 96×96 上 ────────┘
```

**收益**：算力降到 1/33。**代价**：精度损失 —— 但手势识别不需要像素级精度。

> 这是**关键的设计取舍**：把算力花在"信息量最大"的尺度上。

## 四、优化过程

> ⚠ **本节是当前最薄的一节。** 赛题 §3.3.5.5 把"性能与资源优化效果"列为 **20 分**，
> 且 §3.3.4 明确要求"给出**与基线的对比**"。
> **目前只有单点数据，没有完整基线对比表。** 下面列出已有数据与待补项。

### 4.1 已有的实测数据

#### 资源占用（PL 侧，实现后）

| 资源 | 用量 | 占比 | 说明 |
|---|---|---|---|
| Slice LUTs | **11,255** | **21.16%** | |
| Slice Registers | 14,810 | 13.92% | |
| **DSP48E1** | **61** | **27.73%** | ⚠ 主要来自 HLS 的整数除法 |
| Block RAM Tile | 25.5 | 18.21% | |

> 数据取自 `../vivado/build-report.md`（与 `utilization.rpt` 逐项核对过）。

#### HLS 预处理链（csynth 阶段）

| 资源 | 用量 | 占比 |
|---|---|---|
| LUT | 13,184 | 24% |
| DSP | 71 | **32%** |
| BRAM | 34 | 12% |

**关键指标**：
- ✅ **所有循环 `II = 1`**（每周期出一个结果）
- ✅ **Est. Fmax = 137 MHz**（目标 100 MHz，有余量）

#### 时序（实现后）

| 指标 | 值 |
|---|---|
| **WNS** | **+0.265 ns** |
| WHS | +0.051 ns |
| 失败端点 | 0 |
| 结论 | ✅ `All user specified timing constraints are met.` |

> ⚠ **WNS 逐次波动大**：同一设计三次实现为 **+0.873 / +1.177 / +0.265** ns。
> 布线是随机过程。详见 `../vivado/build-report.md` §3.1。

### 4.2 已知且可量化的优化空间

**DSP 占用 27.73%（PL 侧）/ 32%（HLS 侧）偏高，原因明确**：

`thresh_stage` 里的**整数除法**（每像素一次除法）被映射成 DSP48E1 的除法器。

**优化方案**：把"除以 9216"改成**"乘 1/9216 的定点倒数，再右移"** ——
能省下大部分 DSP。

> **这是一份现成的"优化前后对比"素材** —— 改完跑一次 csynth 就能出表格。
> 本作品的 [`../skill/pynq/golden_compare.py`](../skill/pynq/golden_compare.py)
> 的 `report` 子命令就是为生成这张表写的。

## 七、复现说明

```bash
# ① 必须先跑 HLS，产出 IP 仓库（create_project.tcl 依赖它）

vivado -mode batch -source vivado/create_project.tcl -tclargs --synth 0
```
