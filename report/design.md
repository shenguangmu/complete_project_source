## 一、选题背景与创新点

### 1.1 选题：嵌入式手势识别

摄像头实时采集 → PL 侧预处理 → 得到手部轮廓 → 神经网络分类。

**解决的问题**：手势交互需要**低延迟**（跟随动作，不是按一下等一秒）。
这正好落在 FPGA 的强项上 —— **确定性的低延迟流水线**，
而不是 CPU 的"算得快但抖动大"。

### 1.2 面向的竞赛方向

赛题 §3.3.2 的推荐方向里，**"视觉识别"与"图像预处理加速"**都在列。
本作品的定位是**完整的 FPGA 作品**：从摄像头采集一路做到分类结果。

### 1.3 创新点

#### ① 异构划分沿"数据量 × 操作次数"这条线切，而不是沿"难易"切

这是本作品**最核心的设计判断**（详见 §三）。

常见做法是把 CNN 也塞进 PL —— 本作品**明确否掉**，理由是可量化的：

| 约束 | XC7Z020 实际值 | 微型 CNN 全并行的需求 | 判断 |
|---|---|---|---|
| DSP48E1 | **220** | `Conv(1→8, 3×3)` 单层 = 72 个乘法器 | **单层就吃掉 1/3** |
| LUT | 53,200 | 多层流水 + 权重 ROM 寻址 | 会超 50% |
| 动态功耗 | 现有设计约 1.7 W | 全并行会顶到板卡供电/散热上限 | 有风险 |
| 开发工期 | — | 自研 line buffer + 权重调度 + 定标 | **以月计** |
| **替代方案** | — | **Cortex-A9 (650 MHz) 跑定点推理** | **10–30 ms/帧** |

**关键判断**：目标 30 FPS，PS 侧 30 ms/帧**完全够用** ——
因为**瓶颈根本不在推理，在摄像头采集与预处理**。

> **答辩时会被问，所以提前写清**：不是"PL 做不到"，
> 而是**"用最贵的资源解最容易的问题"**。

#### ② 用"接口契约"解耦分工，而不是用接口定义解耦

`DDR 里 96×96 uint8 灰度 buffer` 是**唯一**的跨侧边界（详见 §三）。
两侧各自把它当黑盒 —— **这让 CNN 侧可以在 PC 上独立开发调试**，
不受板子是否到货影响。

#### ③ 把"验证"当成设计的一部分，而不是收尾动作

本作品对每一层都设了**独立的验证手段**（见 [§四](#四优化过程) 与 `../skill/self-correction/`），
且明确区分"已验证 / 未验证"。这个习惯直接产出了
[`../skill/`](../skill/README.md) 里那套可复用的东西。

3. 它用**形态学后处理**，与本作品的 `morph_close` 对应

#### 本作品的差异点

| 维度 | 上述工作 | 本作品 |
|---|---|---|
| 边界 | **分层**：PL 做预处理加速 | **PL 全部**：采集→预处理→DDR 中继 |
| 与下游解耦 | CNN 在 PL 内（①②）或同板 PS（③） | CNN 在**另一侧**，只依赖 DDR 里 96×96 buffer，**可独立开发** |
| 算力取舍 | 尽量把 CNN 加速 | **明确不做 CNN 加速**，算力留给采集与预处理（§1.3①） |

> **一句话**：前人做的是"**把 CNN 放上去加速**"；
> 本作品做的是"**为 CNN 准备一份干净、低延迟的输入**"，
> 并把两侧边界收敛成**一个可验证的数据契约**。

## 二、设计原理与功能框图

### 2.1 系统总览

```
                    ┌──────────────── PYNQ-Z2 (XC7Z020) ────────────────┐
                    │                                                   │
  OV5640            │   PL (可编程逻辑)              PS (Cortex-A9)      │
  ┌────────┐        │  ┌──────────────────┐        ┌─────────────────┐ │
  │ 500万   │  DVP   │  │ 采集 → 灰度 →    │        │ PYNQ Linux      │ │
  │ 摄像头  ├───────►│  │ 高斯 → Sobel →   │  DDR   │  + Jupyter      │ │
  │        │ 14根线 │  │ 自适应阈值 →     ├───────►│                 │ │
  └────────┘        │  │ 形态学 → ROI     │  512MB │  ┌───────────┐  │ │
                    │  └──────────────────┘        │  │ 轻量 CNN  │  │ │
                    │         ▲                    │  │ (他人负责) │  │ │
  ┌────────┐        │         │ VDMA               │  └───────────┘  │ │
  │ 显示器  │◄───────┤  HDMI Out ◄─────────────────┤                 │ │
  └────────┘        │                              │  结果叠加显示    │ │
                    └──────────────────────────────┴─────────────────┘ │
                    └───────────────────────────────────────────────────┘
```

### 2.2 数据通路（两条，从 DDR 分叉）

```
【显示通路】摄像头原图直通，与预处理完全解耦
 dvp_capture ─AXIS(16bit)─► VDMA S2MM ─► HP1 ─► DDR(帧缓存,3帧)
                                                    │
                        VDMA MM2S ◄── HP2 ◄─────────┘
                             │
                             ▼
                     v_axi4s_vid_out ─► （并行视频；TMDS 编码器未做）

【CNN 通路】从 DDR 取同一帧
 DDR(帧缓存) ─► dma_in(MM2S) ─► gesture_preproc ─► dma_out(S2MM) ─► DDR(96×96)
                                                                        │
                                                              PS 侧 CNN 读这里
```

**为什么从 DDR 分叉，而不是从采集侧（`axis_broadcaster`）分叉**：

broadcaster 要求**所有输出都 ready 才接收输入**。
而 `gesture_preproc` 是 HLS 的 `ap_ctrl_hs` 模式 ——
**未 `ap_start` 时 `tready=0`**。CNN 不需要 30 fps，预处理大部分时间空闲，
于是 `gesture_preproc` 空闲 → broadcaster 反压 → VDMA 收不到数 →
**HDMI 显示也一起卡死**。这个反压是**常态化的，不是偶发**。

DDR 分叉的代价是多一次 DDR 往返（614 KB/帧读），三个 HP 口各自独立，占比很小。

### 2.3 时钟域

| 时钟 | 频率 | 来源 |
|---|---|---|
| `clk_fpga_0` | **100 MHz** | PS7 `FCLK_CLK0` |
| `fpga_pl_clk0` | 100 MHz | 同上 |
| `cam_pclk` | **24 MHz** | 摄像头 PCLK（外部输入） |
| `clk_wiz_xclk/clk_out1` | **24 MHz** | Clocking Wizard 输出 → `io_xclk` |

**跨时钟域**：摄像头 PCLK 域 → 系统 100 MHz 域，由 `async_fifo`
（**格雷码指针 + 双时钟**，标准 CDC 做法）处理。

> Clocking Wizard：100 → 24 MHz，**M=12 / D=1 / O=50，VCO = 1200 MHz**。
> **非整数分频，必须用 MMCM**（简单分频做不到）。

## 三、软硬件划分依据与接口设计

### 3.1 划分依据

**一条线**：**PL 做"每像素一次操作"的带宽型任务；PS 做"需要循环迭代与权重"的算力型任务。**

| 判据 | 用 Verilog | 用 HLS | 放 PS |
|---|---|---|---|
| 需要精确控制时钟域/边沿 | ✅ DVP 采集、SCCB 时序 | ❌ | ❌ |
| 需要例化原语（MMCM/IOBUF） | ✅ XCLK 生成、SDA 三态 | ❌ | ❌ |
| "每像素一次运算"的规整流水 | ❌ | ✅ 灰度/滤波/阈值/形态学 | ❌ |
| 需要频繁改参数调优 | ❌ | ✅ 阈值/增益/核大小 | ❌ |
| **需要循环迭代 + 权重的推理** | ❌ | ❌（占满 DSP） | ✅ **CNN** |

**具体分工**：

| 侧 | 承担 |
|---|---|
| **PL 全部**（本项目） | DVP 采集、SCCB 配置、图像预处理链、VDMA、HDMI 输出、DDR 中继 buffer |
| **PS**（他人） | 模型训练、量化、推理、后处理 |
| ~~PL 侧 CNN 加速~~ | **已评估否决**，理由见 §一.3.① |

### 3.2 接口契约（**唯一的一条边界**）

| 项 | 值 |
|---|---|
| **位置** | PS DDR，由 PL 侧的 `dma_out` 写入 |
| **格式** | `uint8` 灰度，行优先连续存放 |
| **尺寸** | **96 × 96**（9,216 字节） |
| **对齐** | 4 字节对齐（DMA 要求） |
| **取值范围** | 0–255，**不做归一化**（归一化由 CNN 侧负责） |
| **物理地址** | 由 PL 侧驱动分配后**写入寄存器**告知 CNN 侧，**不硬编码** |

**为什么这样定**（每条都有理由，不是随手定的）：

- **不归一化** → 归一化是模型侧的事，PL 不该替它做决定
- **地址不硬编码** → 让 CNN 侧可以在 PC 上独立开发调试，不受板子是否到货影响
- **裸 `.bin` 无头** → 加文件头就要两侧同步解析逻辑；裸二进制任何工具都能 `fread`

**握手寄存器**（轮询，暂不用中断）：

| 偏移 | 名称 | 方向 | 含义 |
|---|---|---|---|
| `0x00` | `CTRL` | 写 | bit0 = `capture_start` |
| `0x04` | `STATUS` | 读 | bit0 = `frame_ready`，bit1 = `busy` |
| `0x10` | `INPUT_ADDR` | 读/写 | 96×96 buffer 的物理地址 |
| `0x18` | `FRAME_SEQ` | 读 | 帧序号（丢帧检测用） |

> ⚠ **实现上注意**：HLS 生成的控制寄存器里，
> **`AP_DONE` / `AP_IDLE` 在 `CTRL`(0x00) 的 bit1–bit3**，
> **不在 `0x04`**（`0x04` 是 `GIER`）。
> 这是个经典误用，且**主机仿真发现不了**（仿真自己造了个假 STATUS 值）。

### 3.3 为什么预处理链是"重排后在 96×96 上跑"

预处理链的**标称输入是 640×480**，但**实际计算全部在 96×96 上进行**：

```
crop_scale（640×480 → 96×96）→ 高斯 → Sobel → 自适应阈值 → 闭运算
                              └──────── 全部在 96×96 上 ────────┘
```

**收益**：算力降到 1/33。**代价**：精度损失 —— 但手势识别不需要像素级精度。

> 这是**关键的设计取舍**：把算力花在"信息量最大"的尺度上。

### 4.2 DSP 占用偏高，但**原因与原先的假设不符**

**实测各 stage 的 DSP 分布**（来自各模块的 `csynth.rpt`）：

| Stage | DSP | 说明 |
|---|---|---|
| **`morph_stage`** | **56** | **占全设计的 79%** |
| `crop_scale` | 4 | |
| `thresh_stage` | 2 | |
| `sobel_stage` | 1 | |
| `gaussian_stage` | 0 | |

**`morph_stage` 那 56 个再往下拆**（查 `csynth.rpt` 的 **Bind Op Report** 段）：

| 乘法器 | 位宽 | DSP |
|---|---|---:|
| `mul_64ns_66ns_129_5_1_U134/135/136` | **64×66→129** | **16 × 3 = 48** |
| 其余 8 个小算子 | 14×16→29 等 | 8 |

即 **68% 的 DSP 集中在 3 个宽乘法器上**，来自腐蚀流水线的下标
`r1[yy * width + xx]`（详见 §4.3）。

> ⚠ **本节更正过两次，都值得记**：
>
> **第一次**：原先写的是"DSP 来自 `thresh_stage` 的整数除法"——**错**，
> `thresh_stage` 只占 2 个。
>
> **第二次**：改对归属后，又写"`morph_stage` 的 DSP 来自若干带
> **16 位常数魔数**（如 21846）的乘法器"——**也错**。
> Bind Op Report 里根本没有 21846；真实是 **64 位**宽的乘法器。
>
> **教训**：DSP 的归属要**逐条查 Bind Op Report**，
> 不能凭"哪里有除法""哪里像魔数"推断。本项目在这个问题上
> 连续推断错三次，最后由一个**固定值探针**才定案。

### 4.3 一次失败的资源优化尝试（有数据，负结果）

**动因**：`morph_stage` 占 56/71 个 DSP，想把它降下来。

**完整对照实验**（每次干净重跑，**TB 逐位比对通过**）：

| 改法 | **DSP** | **LUT** | FF | 语义 |
|---|---:|---:|---:|---|
| **基线**（当前，`width` 变量作步长） | **71** | **13,144** | **11,177** | ✅ |
| 步长 `width` → 编译期常量 `96` | 71 | 13,144 | 11,177 | ✅ |
| 9 个读全部显式展开 | **86** ↑ | 13,377 ↑ | 11,698 ↑ | ✅ |
| **探针**：索引换成固定值 | **15** ↓↓ | 10,235 | 8,123 | ❌ 故意破坏 |
| 模板参数化（旧记录） | 71 | — | — | ✅ |

**读法**：

- **探针（第 4 行）证明根因** —— 把 `r1[yy*width+xx]` 换成与循环变量无关的
  固定下标，DSP 从 71 掉到 **15**，那 3 个 64 位乘法器**全部消失**。
  **根因确凿：就是这段索引算术。**
- **但"改不掉"**（第 2、3 行）：
  - 步长改成编译期常量 → **毫无变化**。HLS 对归纳变量的范围推断不足，
    即便步长已知也不收窄位宽。
  - 手写展开 → **反而更差**（DSP +15、LUT +233）。HLS 会把 4 个乘法器
    一起摆上流水线。

**结论**：**找到了根因，但没有不损语义的改法。** 这条路径到此为止。

> ⚠ **负结果也是结果** —— 而且比"没考虑过"更有价值：它带着
> 一组可复现的数据说明"**为什么不能做**"。
>
> ⚠ 但**它仍不能替代赛题要的"性能提升对比"**，
> 见 §4.4。

> **顺带更正一条被推翻的旧结论**：本节曾记录"手写展开/边界分支会让
> II 从 1 退化成 2、关键路径变长会吃掉 `+0.265 ns` 时序余量"。
> 经查证**两处都不成立**：
> - 探针与①的 II 全程都是 **1**，从未退化到 2；
> - **`+0.265 ns` 根本不是本设计的余量** ——
>   全设计 10 条最差 setup 路径**全部属于 AMD 的 `bd_video_v_tc_0` IP
>   内部**（扇出 433 的网、布线 9.122 ns、逻辑仅 0.642 ns），
>   改我们的 RTL/HLS 对它零影响。详见 §4.5。

### 4.5 时序分析：最差路径**不在本设计里**

> 这一节是 2026-09-18 查布线后时序报告得出的，
> **推翻了"我们的设计时序很紧"这个一直以来的印象**。

#### 事实

查 `bd_video_wrapper_timing_summary_routed.rpt`：

**全设计 10 条最差 setup 路径，全部属于 `bd_video_v_tc_0`（AMD 的视频时序控制器 IP）**：

```
Slack (MET) :   0.265ns
  Source / Target :  .../bd_video_v_tc_0/<hidden>/<hidden>/<hidden>   ← 加密 IP 内部
  Path Group      :  clk_fpga_0
  Logic Levels    :  1  (LUT3=1)
  Data Path Delay :  9.764ns  (logic 0.642ns (6.6%)  route 9.122ns (93.4%))
  net (fo=433, routed)  9.122ns      ← 扇出 433 的高扇出网
  Timing Exception:  MaxDelay Path 10.000ns -datapath_only
```

| 事实 | 含义 |
|---|---|
| 逻辑仅 **0.642 ns**、布线 **9.122 ns** | **不是逻辑深度问题**，是布线绕远了 |
| 两端都在 `<hidden>` 的加密 IP **内部** | **改我们的 RTL/HLS 对它零影响** |
| 扇出 **433** | 典型的"高扇出网布线主导" |

#### 与我们自己的流水线对比

| | 目标 | 估计值 | 余量 |
|---|---|---|---|
| `morph_stage` 腐蚀流水线（csynth） | 100 MHz | **143.31 MHz** | **+43%** |
| `clk_fpga_0` 整体（布线后） | 100 MHz | — | +2.65%（**v_tc**） |

HLS 估 143 MHz、整体只有 100 MHz —— **差 30%**。
差异不在 HLS 估错，而在**整体最差路径是 IP 的布线，不是我们的流水线**。

#### 结论：**不优化，如实标注**

| 想法 | 判断 |
|---|---|
| 优化 HLS 流水线 | ❌ 它不是关键路径（余量 43%） |
| 优化我们自己的 RTL | ❌ 10 条最差路径没有一条属于 `dvp_capture` / `gesture_preproc` |
| 去掉 `-datapath_only` 例外 | ❌ 数字会"变好看"，但**那是粉饰**，不做 |
| 给该扇出网加 `MAX_FANOUT` | ❌ 加密 IP 内部网，**约束不进去** |
| 降 `clk_fpga_0` 到 80 MHz | ❌ 违反性能目标（28 → 22 FPS） |

理由：**它在 AMD 官方 IP 内部，是 IP 可用性问题而非本作品的性能瓶颈**。
且**换布线的随机波动比它大**（同一设计三次实现 `+0.873 / +1.177 / +0.265`），
任何"优化"都是在 IP 外面猜 IP 里面的布线。

> 完整的实验数据与复现方式见 [`../src_hls/optimization-report.md`](../src_hls/optimization-report.md)。
