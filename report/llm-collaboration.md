## 二、智能体工作流设计

### 2.1 用 skill 做知识路由，而不是把知识塞进提示词

`fpga-dev` skill 的 `SKILL.md` 是一张**路由表**，不是知识库：

```
| 用户在做什么          | 读哪篇                |
|----------------------|----------------------|
| 写 Verilog            | references/02-...    |
| 搭 Block Design       | references/04-...    |
| **东西坏了/行为诡异**  | references/09-... ← **调试先看这个** |
```

**为什么这样设计**：把 13 篇文档全塞进上下文既超窗口也稀释注意力。
**路由表让模型按现象取用**，而不是按"我知道什么"输出。

### 2.2 验证手段分层：先便宜的，后昂贵的

| 层 | 手段 | 成本 | 何时用 |
|---|---|---|---|
| 1 | `iverilog` + TB | 秒级，**无需 license** | 纯 RTL 逻辑 |
| 2 | 主机侧 C 自检 | 秒级 | PS 侧驱动逻辑 |
| 3 | 桩函数验证 Tcl | 秒级 | 控制流（**⚠ 有陷阱，见 §3.4 模式 3**） |
| 4 | Vivado 综合/实现 | **20–40 分钟** | 最终确认 |

**这条分层是有效的**：本次会话里，前 3 层发现了大部分问题，
第 4 层只跑了几次。

### 2.3 "回读断言"—— 本项目最有价值的方法论沉淀

**核心原则**：**不要让脚本"没报错"当作成功的信号。**

在脚本里对每个关键状态**回读确认**：

```tcl
# 设完顶层，立刻回读
set top_now [get_property top [current_fileset]]
if {$top_now ne "${BD_NAME}_wrapper"} {
    error "顶层设置失败：期望 ${BD_NAME}_wrapper，实际 '$top_now'"
}

# 设完 DDR 参数，立刻回读
set ddr_part [get_property CONFIG.PCW_UIPARAM_DDR_PARTNO $ps7]
if {[string first "MT41K256M16" $ddr_part] < 0} {
    error "DDR PARTNO 未生效，当前值 = '$ddr_part'"
}
```

**为什么必须这样**：Vivado 的多个参数在写错时**只给 WARNING、不中断脚本**，
然后静默取默认值。没有回读断言，你会在 40 分钟后才知道错了。

## 三、纠错轨迹（本项目的核心资产）

### 3.1 人的提问触发了 4 次关键纠正

**这 4 次都不是模型自查发现的。** 如实记录：

| # | 人的提问（原文） | 模型的初始判断 | 实际 |
|---|---|---|---|
| 1 | "能不能改是不是因为**截取了注释内容**" | 以为报错与注释有关 | 是**顶层被设成子模块**，与注释无关 |
| 2 | "**实现时无法完成**" + 一段 DRC 报错 | （未预期） | 追出顶层 bug + 后续 3 个连锁问题 |
| 3 | "**sw 里面的 readme 没有更新吧**" | 声称"已同步 7 个文件" | 实际**漏了 7 个 README** |
| 4 | "**B1, PMOD CAMERA 拓展版**" | 按文档认定选型冲突未决 | 选型其实早已明确 |

**第 3 条尤其典型**：模型的结论是"已同步"，措辞笃定、看起来完整；
是人的一句反问逼出了**完备性检查**（从"我改过哪些"改成"仓库里所有文件"）。

> **对团队协作的启示**：模型擅长**执行**与**追溯**，
> 但不擅长**怀疑自己检查范围的完备性**。这一环必须由人补。

### 3.2 对话摘录

> 以下为用户的原话（**未经润色**）+ 模型当时的回应摘要。
> 保留原始措辞是为了可核查 —— 答辩时可直接对照开发日志。

#### 摘录 A · 第一次报错（把问题问对了，但结论下错了）

**用户**（本次协作的第一条消息）：

> `"E:\complete_project_TCL"` 阅读这个项目，systhsis 报错
> `[Common 17-1257] Failed to create directory 'C'.`
> `[Common 17-354] Could not open 'C' for writing.`
> inmpletion 报错 `[Netlist 29-160] Cannot set property 'iostandard'...`
> 查一下，**能不能改是不是因为截取了注释内容**

**模型**：

- 正确判断出**与注释无关** ✓
- 但把 `17-1257/354` 结论成 **"100% 无害，直接忽略"** ✗

**这个结论后来被实测推翻**（见 [模式 2](../skill/self-correction/README.md)）：
它对产物无害，**但会让 `wait_on_run` 抛错、脚本中断**，导致 XSA 导不出来。

> ⚠ 值得记录的是：用户的提问方向（"是不是注释"）本身也是错的，
> 但那句反问**逼出了主动排查**。**问题问偏了，比不问好。**

> 📌 **本次追加的更正**：摘录 A 里模型那句"100% 无害"后来被实测推翻。
> 而**同一类问题在 2026-09-18 又发生了一次**，且更典型 ——
> 见下方 §3.5、§3.6：**一个错误结论写进注释和文档后，
> 会被后续对话当作前提反复引用**（"16 位常数魔数 21846"、
> "`WNS +0.265` 是我们的余量"都是这样）。
> **摘录的意义不只是"当时错在哪"，还有"错的东西活了多久"。**

#### 摘录 B · "实现时无法完成"

**用户**（附完整 `impl_1` 日志）：

> **实现时无法完成**
> `[DRC NSTD-1] Unspecified I/O Standard: 67 out of 67 logical ports ...`
> `Problem ports: cam_data[7:0], frame_cnt[15:0], line_cnt[15:0], aclk, pclk ...`

**模型**：从日志里读出 `Command: synth_design -top dvp_capture` ——
**顶层被设成了子模块**。追根因 → BD 重建 wrapper 时把它从工程文件表挤掉。

**随后的连锁**：这个修复暴露出**另外 3 个此前被掩盖的问题**
（`open_run` 顺序、重试没绑 `reset_run`、并发竞态）。

> **这是本项目信息量最大的一条用户消息** —— 它只有 5 个字加一段日志，
> 但触发了一整条排查链。

#### 摘录 C · "sw 里面的 readme 没有更新吧"

**用户**：

> **sw 里面的 readme 没有更新吧**

**模型在此之前声称**：

> "已同步 7 个文件 + 新增上板测试指南" —— **措辞笃定、看起来完整**

**实测**：改成"遍历仓库**所有** `.md`"后重查，发现**一共漏了 7 个**。

> ⚠ 这条最能说明 §3.1 的结论：**模型擅长执行与追溯，
> 但不擅长怀疑自己检查范围的完备性**。
> 如果用户没问这一句，这个缺口会一直留到提交。

#### 摘录 D · 选型其实早已明确

**用户**：

> **B1, PMOD CAMERA 拓展版，v1.0 ov540**；B2 顺便可以补，B3 可以找找资料了

**模型此前**把 B1 列为"**文档冲突未决**"的阻塞项，并要求用户拍板。

**实际**：选型早已定为 PMOD-CAMERA，只是**文档间不一致**（契约文档当时按

### 3.3 模型引入的错误（如实记录）

**不是所有错误都来自误判 —— 有一次是模型主动改坏的**：

| 动作 | 理由 | 后果 |
|---|---|---|
| 从工程移除 `rtl/*.v` | "BD 里已有 RTL Module Reference，外部副本多余" | `ERROR: [filemgmt 56-587]`，**综合连启动都启动不了** |

**为什么错**：BD 为每个 RTL Module Reference 生成的 `.xci`
**需要外部源文件才能展开**。移除后无法解析。

**教训**：看到一个"优化机会"时，**先验证它的前提是否成立**，
而不是直接改。这条已写进 `vivado/README.md` 作为反面教材。

### 3.4 四个反复出现的误判模式

整理成**可复用的自检清单**（完整版见
[`../skill/self-correction/README.md`](../skill/self-correction/README.md)）：

| 模式 | 本项目案例 | 通用形式 |
|---|---|---|
| **把"别的文件里没有"当成"这里也没有"** | 误判 `io_xclk` 缺引脚约束 | "X 不存在"必须来自 **X 所在的文件** |
| **只看直接产物，不看谁消费它的后果** | 误判 `Could not open 'C'` 是"无害噪声" | 危害不在它**做了什么**，在**谁把它当信号** |
| **验证了控制流就以为验证了行为** | 桩函数验过重试，但没绑 `reset_run` | 自写的 mock 验证外部交互 = **循环论证** |
| **按"我挑的范围"检查** | 只对比 10 个文件，漏 7 个 | **范围的完备性比检查本身更重要** |

### 3.5 DSP 归属：**3 条错误断言 + 2 次重复尝试，最后靠探针定案**

> 这是本项目**最完整的**一次"假设——被证伪"循环，值得单独记。

**任务**：`morph_stage` 占了 56/71 个 DSP，想降下来。

| 轮次 | 我的结论 | 实际 | 怎么被推翻 |
|---|---|---|---|
| 1 | "DSP 来自 `thresh_stage` 的整数除法" | `thresh_stage` 只占 **2** 个 | 逐模块查表 |
| 2 | "来自带 **16 位常数魔数 21846** 的乘法器" | 全文**没有 21846**；是 3 个 **64×66→129 位**乘法器，每个吃 16 个 DSP | 查 Bind Op Report |
| 3 | "因为 `width` 是变量，换成**编译期常量**就能收窄位宽" | **毫无变化**（71→71，LUT 一模一样） | 跑对照实验 |
| 4 | "那就**完全展开**成 9 个标量读" | **反而更差**（71→**86**，LUT 5214→5447） | 跑对照实验 |
| — | 探针：索引换成**固定值** `r1[0]` | DSP **71→15**，宽乘法器全部消失 | **根因确凿** |

> 📌 **两点如实修正**（回查原始会话后）：
>
> 1. **第 2 轮的措辞比记录里谨慎**。原文写的是
>    "腐蚀 pipeline 里若干带 16 位常数魔数（如 21846）的 `mul_*`，
>    **性质我还没查清就停了**" —— 它**标了不确定**，
>    是后来被转述成"就是 21846"才变成断言的。
>    **标了不确定的结论，在流传中会丢掉那个标记。**
> 2. **第 3 轮不是新错**。那次会话里已经用"改成模板常量 → 71→71"
>    证伪过一次。2026-09-18 的错误是**把已被证伪的假设又试了一遍** ——
>    **因为证伪它的那次没有留下书面记录。**
>    这条正是本节存在的理由。

**结论是"找到了根因，但改不掉"** —— 两条要一起说，
否则下一个人会以为根因没找到而重来一遍。

> **这四轮里，每一轮我都很确定。** 前两轮是"读文档推断"，
> 后两轮是"按推断改代码"。真正定案的是一次**只破坏不改好**的探针 ——
> 它的价值恰恰在于**不试图修复**，只回答"根因在不在这里"。

### 3.6 一个被引用了很久的错数字：`WNS +0.265`

| | |
|---|---|
| **它被引用了多少处** | **4 个文件、7 处**，且都写成"我们的时序余量不大" |
| **它实际是什么** | AMD `bd_video_v_tc_0` IP 内部一条**扇出 433** 的网：逻辑 0.642 ns、布线 9.122 ns |
| **怎么发现的** | 想把 `0.265` 和 HLS 估的 `143 MHz` 对上，**对不上**（差 30%），于是去查它到底属于谁 |
| **真相** | 全设计 10 条最差 setup 路径**全部属于那个 IP**，改我们的 RTL/HLS 零影响 |

**教训**：**引用一个数字前，先确认它属于谁。**
`0.265` 一开始只是"时序报告里最显眼的那个数"，
被引用几次之后就变成了"我们的余量" —— 没人回头查过它的归属。

> 这一条比 DSP 那几条更值得警惕：**错误在文档里传播，比在代码里更难发现**，
> 因为代码错了 csim 会报，文档错了**谁都不会报**。

## 四、哪些做法被实测证明有效 / 无效

**如实区分** —— 赛题明确要求"数据是否真实完整"。

### ✅ 有效（有实测证据）

| 做法 | 证据 |
|---|---|
| 回读断言 | 两次真实拦下错误（顶层、DDR 参数） |
| `iverilog` 分层验证 | 秒级跑完 3 个 TB，无需 license |
| 带 `reset_run` 的重试 | 实测一次运行 10 个子 run 中招，重试全部恢复 |
| 失败子 run 诊断（遍历而非 glob） | 实测正确列出 10 个名字 |
| **"只破坏不改好"的探针** | 一次定案 DSP 根因（71→15）；此前"边猜边改"的 4 次**全错**（见 §3.5） |
| **每次对照实验都跑 csim 逐位比对** | 保证结论不是"综合过了就算"，四条实验全部 `TB PASSED` |
| **台账式核对数字** | 从 `csynth.rpt` / `utilization.rpt` 逐字读，不再凭记忆（见下） |

### ❌ 无效 / 有陷阱

| 做法 | 问题 |
|---|---|
| **凭记忆写资源数字** | `LUT 13,184`、`Fmax 137 MHz` 在 3 个文档里错了很久（实际 `13,144` / `143.31 MHz`）。**代码错了 csim 会报，文档错了谁都不会报** |
| **引用数字不查归属** | `WNS +0.265` 被引用 7 处，没人问过"它属于哪个模块" —— 结果是 AMD IP 的（§3.6） |
| **"找到根因"就当成"能改"** | 探针证明了根因，但两条改法**都更差**。两者必须一起写进结论 |
|---|---|
| **桩函数验证 Tcl 控制流** | 见 §3.4 模式 3 —— **循环论证**，掩盖了真 bug |
| 用 `get_runs "${name}_*"` 找子 run | glob 匹配不到，诊断**静默失效**（一行没输出） |
| "产物齐全 + 返回码 0" 判定无害 | 见 §3.4 模式 2 —— 忽略了批处理流程的信号依赖 |

### ⚠ 未验证（不能声称有效）

| 项 | 状态 |
|---|---|
| 上板实测 | **完全未做**（板子未到） |
| OV5640 配置表内容 | 换成了真表，但**未上板验证出图** |
| PYNQ 镜像与 Vivado 2025.2 兼容性 | 未验证 |

> **这一节的意义**：答辩会问"你的数据可复现吗"。
> 主动区分"已验证 / 未验证"，比声称"全都能跑"更可信。
